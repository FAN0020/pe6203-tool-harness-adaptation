Tool Harness Adaptation
under Environment Change

PE 6203 Group Project 4 | Final offline audit | 31 October 2026

Research questions

Does updating affected tool knowledge recover task performance after persistent tool-environment change? Does it preserve capabilities on tasks whose tools remain unchanged? We evaluate quality, efficiency, cross-version stability, update cost and execution status separately; no weighted score is introduced.

Abstract

We implement a deterministic Selective Patch that compares tool metadata, expands the affected set through explicit dependencies, updates affected records and preserves unaffected knowledge. The same fixed DeepSeek model executes a documented three-task MCPEvol-Bench subset in Early, Middle and Late environments under No Update, Full Rewrite and Selective Patch. One execution per cell gives 27 trajectories, each with five valid judge ratings.

Independent recalculation from the frozen raw archive confirms that Selective Patch has the highest observed mean Planning Effectiveness (9.1111), but lower mean Task Fulfillment (9.8889), population ECS (9.7318) and normal completion (6/9) than both baselines. It uses zero model tokens for updating, tied with No Update, and 1.145 seconds of local update time. Its changed-task TF gain relative to No Update is 0 in Middle and +0.1 in Late; unchanged-task TF is retained.

The results establish a runnable, auditable course experiment. They do not establish general superiority, statistical significance or broad generalization. Early arms share identical knowledge, yet exhibit different truncation and completion outcomes. This variation materially affects ECS.

1. Method and architecture

A harness stores tool names, input schemas, descriptions, usage rules, output schemas and routing. Persistent environment changes can make these records stale even if the base model remains fixed. Our intervention is the tool-knowledge snapshot presented to the agent, not model fine-tuning.

Adaptation pipeline

Early knowledge K0 + target-stage metadata
        -> deterministic add / remove / field diff
        -> affected records + explicit one-hop dependencies
        -> copy authoritative target fields for affected records
        -> preserve unaffected records and valid usage rules
        -> schema / routing / preservation validation
        -> frozen knowledge Kt -> common agent -> real MCP tools
        -> raw trajectory + five judge ratings + independent analysis

Tool identity is server_id::name. The comparison covers name, parameters, description, output_schema and routing; a rename without stable identity evidence is treated as removal plus addition. Structural changes propagate through explicit tool references in usage rules. Target metadata is authoritative for structural fields. Usage rules are preserved rather than erased by an empty metadata field; unresolved semantic dependencies are recorded. The evaluated Selective Patch performs no LLM update calls.

MethodKnowledge policy
No UpdateRetain the Early snapshot K0 after environmental change.
Full RewriteRebuild all target records and use the fixed LLM to regenerate every target description; protect schemas, routes and supplied rules.
Selective PatchUpdate affected records by deterministic diff and dependency expansion; preserve unaffected records.

All three methods use the same execution agent to choose tools, arguments and next steps. Candidate MCP servers come from the official task. No task-specific call sequence is scripted. Early uses common K0 in every arm. This implementation compares both update scope and description-generation mechanism; it is not a pure scope-only ablation.

Cross-version ECS

For each task, first compute the mean of its three TF values, then subtract their standard deviation. ECS is the average of these task-level quantities. It is not computed by subtracting the spread of three overall stage means.

mu_t = (TF_early + TF_middle + TF_late) / 3
sigma_population = sqrt(sum((TF_i - mu_t)^2) / 3)
sigma_sample     = sqrt(sum((TF_i - mu_t)^2) / 2)
ECS = mean_over_tasks(mu_t - sigma_t)

The released implementation uses population standard deviation; the paper appendix specifies the sample convention. Both are reported, with population as the primary implementation-compatible result. For Selective Patch, task 133 TF=[9, 10, 10] gives task ECS 9.1953 (population) or 9.0893 (sample); tasks235 and 283 each give10. Therefore overall ECS is 9.7318 or9.6964.

The low Early TF on task 133 occurred with common K0 and output truncation. It reduces the Patch ECS, but cannot be attributed to a patch that was not yet applied. Conversely, higher subsequent TF is not automatically a pure update effect.

7. Failure evidence: under-update and confounds

We classify a stated claim as confirmed (direct mechanism evidence), suggestive (plausible but confounded), inconclusive (insufficient evidence), or contradicted (inconsistent with stored knowledge/calls). Confirmation of a local failure does not establish a general strategy effect.

U1 - Confirmed stale No Update call failure

Task 133 Late: Early validate_syntax requires expression only; Late also requires allow_variables. No Update keeps the Early schema. Four initial validation calls omit allow_variables and are rejected; later calls add the parameter after reading errors. The agent completes with TF 9.8/PE 7.2 after 38 calls. The stale-schema-to-rejection chain is direct, but it is a No Update observation, not a Selective Patch under-update example.

U2 - Contradicted omission attribution for Patch

The main Selective Patch artifact contains the required field and its three validate_syntax calls explicitly pass allow_variables. It completes with TF 10/PE 7, four total calls and zero tool errors. Calling this a missed parameter update would contradict the actual records.

B1 and P1 - Different failure mechanisms

Task 133 Early Patch truncates in round 2 with TF 9/PE 10, although every Early arm has identical K0. An update-caused explanation is contradicted. Task 283 Late Patch reports review_workspace_health failing because listMemories is missing; it also has two empty-argument create_task errors, an API retry and round exhaustion. The tool error is observed directly, but its contribution to the terminal failure is not isolated. Neither should automatically be called under-update or over-update.

8. Failure evidence: over-update and negative results

O1 - Suggestive historical Full Rewrite regression

In the older task 235 Late cohort, all 28 chart records are unchanged across environments. Full Rewrite nevertheless regenerates every description. Its trajectory makes five map calls and omits map-unit metadata, with TF 8.8/PE 4.2 versus 10/10 for the other arms. However, the rewritten description explicitly mentions dataValueUnit. The omission therefore cannot be explained as guidance simply disappearing. The regression is not itself proof that rewriting caused damage, and this is Full Rewrite rather than Selective Patch.

O3 - Inconclusive causal attribution after negative diagnostics

Six existing controlled description-rollback executions, three per arm, all complete with TF/PE 10 and three tool calls. They do not reproduce the historical damage. We retain this negative result and do not repeat it until a desired effect appears. It does not establish that harmful rewrites are impossible.

O2 - Suggestive scope expansion in linked_notes

A historical research variant adds this rule to metadata-unchanged math-mcp::evaluate:

validate_syntax now accepts optional detailed and allow_variables flags; evaluate's validate_only remains a separate syntax-only path, so choose based on whether evaluation is also wanted.

The task 133 Middle trajectory performs two syntax checks and a security-prompt call, then three evaluate calls. It completes with TF 10/PE 5; original Patch in that cohort uses three calls and scores 10/10. Four usage-rule records differ between these arms, so the note is not an isolated treatment. Also, evaluate is semantically related to the changed validator: metadata-unchanged does not necessarily mean unrelated. This is a suggestive research-variant case, not a confirmed failure of the main method.

Judge limitation: correct scores are not corrected answers

A fresh factual review of the six diagnostic answers finds three claiming the monthly sales sum is 24.4M: rewrite-r0, rewrite-r2 and rollback_descriptions-r0. The supplied 12 numbers sum to 25.4M. All three retain their original TF/PE 10. Errors in both arms weaken any claim of rewrite-specific factual harm and demonstrate that high judge ratings can miss answer defects.

Unresolved over-update evidence: a later one-rule retained/reverted comparison is suggestive, but the rule concerns a related validator and cannot be assumed unrelated. Thus neither that pair nor the negative chart rollback establishes the full unrelated-change-to-damage chain required by the definition. See Appendix E. Lack of natural occurrence is not the acceptance criterion.

Evidence: case-details/O1.json and O2.json contain exact descriptions/rules; diagnostic-review.json identifies all six trajectories; raw answers and five ratings remain unchanged.

9. Interpretation and limits

Supported observations

Selective Patch updates tool knowledge without model calls and prevents the specific initial missing-parameter errors seen in No Update task 133 Late. In this cohort it retains task 235 TF and has the highest mean PE. Full Rewrite leads the mean TF and ECS comparisons; both baselines have more normally completed runs. These outcomes can coexist and do not require a composite winner.

What the data do not establish

One execution per cell on three tasks is not enough to estimate robust strategy-level uncertainty, frequency of rare failures or generalization to the full benchmark. Temperature0 does not make provider execution deterministic. Five judge ratings characterize one saved trajectory, not run-to-run agent variance. No inferential significance claim is made for the27-run main cohort.

TF is near the scale ceiling, and incomplete trajectories can receive high TF. Early differences under identical K0 affect cross-version scores. The same model family acts as agent and judge. Rubric interpretation of distinct security checks and redundant calls is imperfect; manual factual findings are reported separately, never silently substituted for ratings.

The subset lacks required tool removal/renaming, uses optional tool additions, and is not an unseen-family holdout. The runner uses native stdio and common local adaptation plumbing, rather than an exact recreation of every paper infrastructure choice. Full Rewrite and Patch differ in both update scope and generation mechanism. Public MCP package defects are kept common across arms.

Reuse of prior work

The completed 108-trajectory research confirmation contains 81 executions of the original three methods with three repeats each. It can serve as a separate robustness appendix, alongside its fourth candidate and negative promotion result. Its frozen Full Rewrite artifacts and shared-build protocol differ from the main cohort, so results are not pooled. Sixty research development trajectories, old A/B cohorts, incomplete confirmations, generation rejections and negative diagnostics remain available as history.

The historical PE+0.5 and statistical-promotion thresholds are not course completion requirements. Netlify/task 223 is an optional custom deployment demonstration; it is not required to complete the fixed 27-cell experiment and is not run here. VPN involvement is possible in past connection failures, but not established as their cause.

Stopping rule

Stop strategy optimization and further execution. Review the evidence with the group and seek TA clarification on controlled cases and the implemented Full Rewrite scope. The outstanding issue is strength and relevance of evidence, not whether failures arose naturally or whether Patch beats a baseline. No more diagnostics, 81/108-cell matrices or deployment are authorized.
